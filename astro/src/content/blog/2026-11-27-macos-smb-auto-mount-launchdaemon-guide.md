**macOS SMB Auto-Mount with LaunchDaemon · Practical Guide**

如果一台 Mac 长期承担文件服务器、自动化节点或 AI 工作站的角色，那么它访问 NAS 的方式就不能只依赖某个人登录桌面后手动挂载共享目录。

问题在于：macOS 重启以后，如果没有用户登录，普通的登录项或用户级自动化通常不会按预期运行。机器虽然已经开机，依赖 NAS 文件的后台任务却可能因为共享目录没有挂载而无法工作。

本文记录一种已经在实际设备上完成重启验证的思路：使用 **System LaunchDaemon** 在系统启动阶段执行检查，由 root 管理系统服务和受保护的凭证，再切换到专用的普通 macOS 用户执行 SMB 挂载。真实挂载点放在该用户的私有目录中，最后用符号链接兼容原有访问路径。

这是一篇通用技术实践记录，不依赖某个企业的内部网络、设备名称或账号配置。不同 macOS 版本、NAS 配置和安全策略可能存在差异，部署前仍需在自己的环境中测试。

## 一、先弄清楚：我们要解决的是什么问题？

常见的手动挂载方式类似：

```bash
mount -t smbfs //smb-user@nas-host/Share /Volumes/Share
```

它适合临时连接，但不等于系统启动后一定会自动恢复。尤其当任务运行在后台、机器没有用户登录桌面时，依赖登录会话的自动化就可能失效。

一个可靠的系统级方案，至少要满足这些要求：

- Mac 启动后能够自动检查 NAS 连接。
- 不要求用户先登录图形桌面。
- NAS 使用专门的 SMB 账户进行认证。
- 实际挂载由权限受控的普通 macOS 用户执行，而不是默认以 root 身份访问文件。
- SMB 密码不出现在命令行参数、LaunchDaemon 配置或普通日志中。
- 本机其他普通账户不能直接浏览该挂载目录。
- 尽量保留现有应用使用的文件路径。
- 网络尚未就绪或 NAS 暂时不可用时，能够自动重试。

这里要区分两个身份：**NAS 上的 SMB 账户**负责决定远端共享允许访问什么；**Mac 上的本机账户**负责决定本地哪个用户拥有挂载目录。它们不是同一个账户，也不代表 NAS 能识别每一个本机员工的个人身份。

## 二、为什么选择 LaunchDaemon，而不是 LaunchAgent？

macOS 的 LaunchAgent 和 LaunchDaemon 都由 launchd 管理，但运行范围不同。

| 项目 | LaunchAgent | LaunchDaemon |
|---|---|---|
| 运行范围 | 用户登录会话 | 系统级 |
| 是否依赖用户登录 | 通常依赖 | 不依赖图形桌面登录 |
| 常见用途 | 用户应用、桌面辅助任务 | 系统服务、后台维护任务 |
| 本场景是否合适 | 不适合作为唯一机制 | 更适合 |

如果目标是“机器开机后，即使没有人登录桌面，也要恢复 NAS 连接”，那么系统级 LaunchDaemon 更符合需求。

LaunchDaemon 通常由 root 管理和启动，但这不意味着它启动的所有操作都必须以 root 身份执行。可以让系统服务负责检查、读取受保护的凭证和协调流程，再通过明确的用户切换机制，让实际 SMB 挂载由专用普通用户完成。

这一区分很重要：**管理系统服务的权限，不应自动变成访问共享文件的日常身份。**

Apple 的归档开发者指南说明，系统级 daemon 配置位于 `/Library/LaunchDaemons`，用户 agent 则随用户登录会话启动；它也列出了 launchd 的周期触发方式。可以先阅读 [Apple《Creating Launch Daemons and Agents》](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)，再对照目标 macOS 版本的本机手册。

## 三、最终架构：root 管理，普通用户挂载

推荐把流程拆成几个边界清晰的部分：

```text
macOS 启动
    |
    v
System Launchd
    |
    v
LaunchDaemon 包装脚本
    |
    v
Root Credential Helper
    |-- 读取受保护的 SMB 凭证
    |-- 检查当前挂载状态
    |-- 准备私有挂载目录
    |
    v
切换为专用 macOS 普通用户
    |
    v
mount -t smbfs
    |
    v
NAS SMB Share
    |
    v
用户私有目录中的真实挂载点
    |
    v
可选：/Volumes 下的兼容符号链接
    |
    v
后台应用与自动化任务
```

这套架构有四个关键组件：

1. **LaunchDaemon**：负责在系统启动时运行，并按设定间隔重新检查。
2. **Root Helper**：以受控方式读取凭证、检查挂载状态并协调挂载过程。
3. **普通用户挂载**：真正的 SMB 文件系统操作由专用本机用户执行。
4. **兼容路径**：如果旧应用依赖固定路径，可以通过符号链接保留原来的访问入口。

不要把所有逻辑都塞进一个以 root 运行的 Shell 脚本。凭证处理、挂载身份和路径管理应该各自有清楚的职责。

## 四、为什么不直接把 SMB 挂载到 /Volumes？

最初看起来最直接的做法，是让 root 创建 `/Volumes/Share`，修改目录所有权，再切换为普通用户挂载。

但在实际排查中，曾出现 root 能看到挂载点、切换到普通用户后却无法正常访问该路径的情况。继续围绕 `/Volumes` 修改权限并没有解决根本问题。

原因在于，`/Volumes` 是 macOS 常用于卷挂载的系统路径，不适合在不了解其生命周期和系统行为的情况下，当作普通业务目录反复修改。

更稳妥的思路是：**把真实挂载点放在专用用户拥有的私有目录中，再把旧路径作为兼容入口。**

例如：

真实挂载点：

```text
/Users/smb-service/.nas-mount/Share
```

兼容路径：

```text
/Volumes/Share
```

符号链接关系：

```text
/Volumes/Share
    -> /Users/smb-service/.nas-mount/Share
```

这样做有两个好处：

- SMB 挂载点由实际执行挂载的用户管理，不需要依赖 `/Volumes` 的目录创建和权限行为。
- 原本使用 `/Volumes/Share` 的脚本或应用可以继续使用原路径，不必一次性修改所有调用方。

符号链接只是路径兼容层，不是权限边界。真正的访问限制来自目标目录及其父目录的权限。

## 五、本机权限与 NAS 权限要分开设计

这套方案至少涉及三个身份：

| 身份 | 所在位置 | 主要职责 |
|---|---|---|
| SMB 服务账户 | NAS | 验证 SMB 会话，决定远端共享访问范围 |
| macOS 服务账户 | Mac | 执行挂载并拥有本地挂载目录 |
| root | Mac | 管理 LaunchDaemon、受保护凭证和系统级辅助程序 |

### 5.1 使用专用的普通 macOS 账户

建议创建一个专门用于后台文件访问的本机账户，不要直接把日常桌面账户当作系统服务账户。

真实挂载目录可以设置为该账户所有，并使用 `0700` 权限：

```bash
chmod 700 /Users/smb-service/.nas-mount
```

`0700` 表示只有目录所有者具有读取、写入和遍历权限，组用户及其他用户没有权限。

实际部署时，还需要检查父目录的遍历权限、挂载点本身的权限，以及 SMB 文件系统挂载后的实际访问行为。不能只看符号链接的权限，就判断目标文件是否安全。

### 5.2 NAS 端仍然使用原有 ACL

本机目录权限不能代替 NAS 权限。

NAS 仍然应该通过 SMB 服务账户和共享目录 ACL 控制远端访问范围。不要为了让 Mac 挂载成功，就把共享目录改成所有人可读写，也不要随意把服务账户加入管理员组。

还要明确一个边界：当多个本机应用都通过同一个 SMB 服务账户访问 NAS 时，NAS 看到的是这个共享服务身份，而不是每个应用背后的员工身份。若业务需要按员工审计或分别授权，应另行设计身份认证和访问机制。

## 六、如何安全保存 SMB 凭证？

不要把 SMB 密码直接写在以下位置：

- Shell 命令参数；
- LaunchDaemon 的 plist；
- 普通用户环境变量；
- 会被其他用户读取的配置文件；
- 日志或调试输出。

一种可行的实现是使用 root 管理的独立凭证文件，例如：

```text
/var/db/example-smb-mount/credential
```

凭证目录和文件应由 root 管理，文件权限限制为仅 root 可读写（例如 `0600`）。具体文件格式由辅助程序定义，不要把示例路径或格式直接照搬到生产环境。

辅助程序再通过受控的输入通道，把密码提供给 SMB 客户端。实际案例采用私有 PTY 处理认证输入，避免把密码放进进程参数。

需要特别说明：

- 凭证文件权限只能限制普通账户读取，不能防御拥有 root 权限的进程。
- 私有 PTY 是一种实现方式，不是所有环境都必须照搬的唯一方案。
- 不要在调试时打印密码，也不要用会把密码展开到命令行的写法。
- 如果需要防范设备丢失或磁盘被拆下后读取数据，应启用并正确管理 FileVault 等全盘加密机制。
- 备份时也要把凭证文件视为敏感数据，不能随意复制到共享目录。

## 七、让 LaunchDaemon 自动检查和重试

只设置一次开机执行仍然不够。Mac 启动时，网络可能还没有准备好，NAS 也可能正在重启。

一种简单的恢复机制是让 LaunchDaemon 在加载时执行一次，并以固定间隔再次检查。例如每 60 秒检查一次：

```xml
<key>RunAtLoad</key>
<true/>
<key>StartInterval</key>
<integer>60</integer>
```

这只是 LaunchDaemon 配置中的两个关键字段，不是完整可直接安装的 plist。完整配置还需要根据实际程序路径、参数、日志位置和系统要求编写，并验证文件所有者、权限及 launchd 加载结果。

每轮检查的逻辑可以保持简单：

1. 检查目标共享是否已经正确挂载。
2. 如果已挂载，正常退出，不重复挂载。
3. 如果未挂载，检查网络和凭证，然后尝试建立连接。
4. 如果网络或 NAS 暂时不可用，记录不含敏感信息的错误，退出并等待下一轮。
5. 如果发现挂载点状态异常，按明确的恢复策略处理，不要直接强制卸载仍在使用的文件系统。

这种设计属于周期性检查，不要求辅助程序一直占用后台进程。

### 一个容易误判的状态：not running

LaunchDaemon 的任务执行完毕后，进程自然会退出。因此，看到服务显示 `not running`，不一定代表故障。

应该综合检查：

- 服务是否已经被系统加载；
- 是否配置了 `RunAtLoad` 和预期的重试间隔；
- 最近一次运行是否成功；
- 实际 SMB 文件系统是否已经挂载；
- 挂载是否由预期的本机用户执行；
- 兼容路径是否指向真实挂载点；
- 是否能够读取共享中的实际文件。

**判断系统服务是否正常，不能只看它此刻有没有一个常驻进程。**

## 八、部署前后的检查方法

下面是常用的检查命令。请将示例路径和服务标识替换为自己环境中的实际值。

### 8.1 检查 LaunchDaemon

```bash
sudo launchctl print system/com.example.smb-mount
```

重点关注服务是否存在、运行次数、最近退出码和触发配置。

### 8.2 检查 SMB 挂载

```bash
/sbin/mount | grep smbfs
```

不要只判断命令是否有输出，还要确认挂载源、目标路径以及挂载执行身份是否符合预期。

### 8.3 检查真实挂载点的所有权和权限

```bash
stat -f '%N owner=%Su uid=%u group=%Sg gid=%g mode=%Sp' \
  /Users/smb-service/.nas-mount/Share
```

### 8.4 检查兼容路径

```bash
ls -ld /Volumes/Share
readlink /Volumes/Share
```

### 8.5 检查实际文件读取

```bash
/bin/ls -la /Volumes/Share/
```

建议使用目录路径末尾的斜杠，便于明确检查的是链接目标中的目录内容。

### 8.6 查看日志

```bash
tail -100 /var/log/example-smb-mount.log
```

日志中不要记录密码、完整凭证内容或不必要的敏感文件名。历史日志可能保留早期失败信息，判断当前状态时应以最近一次执行结果和实际挂载状态为准。

## 九、重启验收：不要只验证“当前能访问”

手动挂载成功，只能证明当前会话可以连接 NAS；它不能证明系统启动后能够自动恢复。

完整验收至少应包含：

| 验收项目 | 检查内容 |
|---|---|
| 无桌面登录启动 | 重启后不登录图形桌面，系统服务仍能执行 |
| 自动连接 | NAS 共享在启动后自动挂载 |
| 挂载身份 | 实际挂载由指定普通 macOS 账户执行 |
| 本机权限 | 其他普通账户不能遍历私有挂载目录 |
| NAS 权限 | 只能访问 SMB 服务账户原本获准访问的目录 |
| 路径兼容 | 旧应用使用的路径仍能访问 |
| 文件读取 | 能够实际列出并读取共享文件 |
| 网络恢复 | 网络暂时不可用时，后续检查能够重新连接 |
| 凭证保护 | 凭证不出现在参数、普通日志或公开配置中 |

还应单独测试 NAS 重启、网络断开后恢复、SMB 会话失效等情况。一次重启通过不代表所有异常场景都已经覆盖。

## 十、常见故障应该从哪里查？

| 现象 | 优先检查 |
|---|---|
| 开机后没有挂载 | LaunchDaemon 是否加载、网络是否就绪 |
| Authentication failed | SMB 账户、密码和 NAS 端权限 |
| 凭证读取失败 | 凭证文件所有者、权限和格式 |
| 普通服务账户无法访问 | 挂载身份、目标目录和父目录权限 |
| 其他本机账户也能访问 | 私有目录权限、父目录遍历权限和实际挂载参数 |
| 兼容路径不存在 | 符号链接是否创建、目标路径是否存在 |
| 服务显示 not running | 检查运行次数、退出码和真实挂载状态 |
| 网络恢复后仍未挂载 | 重试任务是否继续触发、错误处理是否正确 |
| 文件能列出但无法读写 | NAS ACL、SMB 会话权限及文件系统实际行为 |

遇到权限问题时，不要把目录改成 `777` 作为快速解决办法。这样做可能掩盖真正的身份或权限配置错误，还会扩大本机文件暴露范围。

## 十一、这套方案适合什么场景？又不适合什么场景？

它适合：

- 长期运行的 Mac mini、Mac Studio 或其他 macOS 主机；
- 需要在无人登录桌面时运行的后台自动化；
- 需要访问 NAS 文件的构建机、媒体处理节点或 AI 工作站；
- 希望保留既有共享路径、又需要系统级自动恢复的环境。

它并不自动解决：

- 多名员工各自的 NAS 身份透传；
- NAS 端的细粒度权限设计；
- root 权限进程的访问限制；
- 多台 Mac 之间的凭证分发和轮换；
- 网络断开时正在进行的文件写入如何保证一致性。

如果只是个人 Mac 偶尔访问 NAS，Finder 的连接服务器或用户登录后的自动挂载可能已经足够。只有当机器需要在无人值守状态下持续运行后台任务时，才有必要引入系统级服务和专用凭证管理。

## 十二、总结：把文件访问变成可靠的系统基础设施

这次实践最重要的收获，不是找到一条更复杂的挂载命令，而是把几个容易混在一起的问题拆开处理：

- **LaunchDaemon** 负责系统启动和周期检查；
- **Root Helper** 负责受保护凭证和系统级协调；
- **专用普通用户** 负责真正的 SMB 挂载；
- **私有目录** 负责本机访问隔离；
- **符号链接** 负责兼容既有文件路径；
- **周期性检查** 负责在网络或 NAS 暂时不可用时重新尝试。

这套设计让 NAS 文件访问不再依赖某个人是否登录桌面，也避免为了方便而把共享目录权限放大。

最后提醒：macOS 的系统服务、SMB 客户端和文件系统行为可能随系统版本变化。本文提供的是经过实际环境验证的架构思路，而不是可以不经检查就复制到所有 Mac 上的安装脚本。部署时应先理解每个组件的权限边界，再根据设备、账户和共享配置完成测试。

**核心原则：让系统服务负责恢复连接，让专用普通用户负责文件访问，让 NAS 自己的 ACL 继续负责远端授权。**
