01 / 理念

不是另一个聊天机器人，而是企业的 AI 运行层。

EAO 不试图替代成熟的 RAG 引擎、Agent 框架、Web 客户端或业务系统。它通过可复现的企业架构把这些能力连接起来，并明确权限、知识与执行边界。

传统 AI

员工 → Chatbot → 回答

能够完成对话，但通常与组织结构、企业知识和受治理的执行过程相互割裂。

Enterprise AI Office

员工 → 部门 Assistant → 企业知识 → Agent + 工具 → 工作

AI 成为组织查找信息、推理、执行工作并维持运行边界的一部分。

02 / 能力

用一组必要能力，构成完整的企业 AI 办公系统。

01

部门 AI

通过专用 Hermes Profiles，让不同部门拥有各自的 Assistant、工具、知识范围与最小权限执行边界。

02

企业知识

WeKnora Document/RAG 负责基于事实的检索；Native Wiki 保存可复用、经过整理的业务知识。

03

工作历史

EAO Ledger 记录有边界的事件、工作与内容历史，同时避免把通用 Memory 变成第二个事实来源。

04

企业文件

Catalog-first Enterprise Archive 高效发现外部文件，并通过查询时授权读取来保持访问边界。

05

Agent 执行

Hermes Agent 将 Assistant 连接到获准使用的工具与行动，并提供有边界的执行可见性，而不是暴露隐藏思维链。

06

运行治理

Control Plane、Boundary Principles、健康检查、升级、回滚、恢复与验收证据共同保证系统可维护。

03 / 架构

上游优先。薄集成。清晰归属。

EAO 有意围绕成熟项目构建，而不是 Fork 它们。EAO 自身只负责系统设计、部署契约、治理边界，以及让整套技术栈作为一个企业系统协同运行所需的薄适配层。

04 / 设计原则
使用足够完成任务的最轻执行路径。任何复杂性都必须证明自身价值。

人类身份 ≠ Agent 身份

人员、Agent Profiles 与模型供应商凭证保持为彼此独立的权限域。

Knowledge ≠ Memory ≠ History

RAG、Wiki、Ledger、Archive 与可选的 Agent Memory 各自承担不同职责，并拥有不同的事实来源。

能力优先于基础设施

优先复用上游成熟能力；只有真正存在缺口时，才增加自定义基础设施。

简单任务保持简单

Kanban 与多 Agent 委派属于兜底能力，而不是每项任务都必须经过的流程。

变更必须有边界

通过 Workspace、任务、Agent、变更与权限边界限制影响范围，而不是再引入沉重的工作流引擎。

生产状态必须有证据

健康、恢复、访问与验收检查，用来区分“能演示”与“真正可运行的企业部署”。

05 / 参考实现

来自真实部署，并为复用而设计。
